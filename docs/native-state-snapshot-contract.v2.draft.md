# Native State Snapshot Contract v2 — Draft

**Status:** bounded Stage 1 B implementation contract; review required.  
**Supersedes:** Native State Snapshot Contract v1 for the enriched unit/position fields.  
**Tracking:** #346, #293 and #294.

## 1. Prior problem

Snapshot v1 carried unit UUID, champion, star and item catalog IDs, but did not publish the unit's exact static catalog trait membership or identify the native board-slot geometry. UUID generation was deterministic and scoped only implicitly by the factory lifetime; the wrapper did not reject a duplicate UUID appearing in two active owner/location rows.

## 2. Technical rationale

The structured producer boundary must expose facts already owned by the native catalog and Engine without inventing strategic state. Physical unit identity must be interpreted in its enclosing Engine/episode/player scope, while the native factory must reject duplicate UUID issuance within one episode. Position must state the coordinate convention actually implemented, not imply canonical TFT hex semantics.

## 3. New responsibility and owners

- `UnitInstanceFactory` owns UUID issuance and per-factory duplicate rejection. The factory is recreated at episode reset.
- `TFTEngine::get_audit_snapshot` owns the immutable unit, trait-membership and board-geometry projection.
- `ChampionDefinition::traits` is the sole source for `trait_names`.
- Pybind transports the v2 fields without reinterpretation.
- `CppTFTLobbyWrapper` validates the contract version, geometry, trait membership and uniqueness of active UUIDs across all players and locations.
- Trainer/RolloutBuffer continue to retain this snapshot as non-tensor correlation metadata.

## 4. Contract and invariants

### Unit identity

The canonical scoped identity for a unit row is:

`(engine_instance_id, episode_id, player_id, uuid)`

- `uuid` is generated by the episode-scoped `UnitInstanceFactory`.
- The factory rejects a UUID collision within its lifetime instead of publishing a duplicate.
- The enclosing snapshot supplies Engine and episode identity; the player record supplies owner identity; the containing board/bench/shop array supplies location and slot.
- One active physical copy may appear in exactly one board, bench or shop slot across the eight players in a snapshot.
- UUID may repeat after episode reset or in another Engine instance; those are different scoped identities.
- Shop-offer identity remains separate: the offer revision and slot are not replaced by UnitInstance UUID.

### Trait membership

- `trait_names` is copied verbatim from `ChampionDefinition::traits`.
- It describes static catalog membership for that champion definition.
- It is not an active trait count, completed milestone, strategic focus/core trait, or item-granted trait.
- The wrapper requires a list of non-empty unique strings; empty slots must publish an empty list.
- Trait catalog membership does not become an Actor/Critic tensor feature merely because it is present in the audit sidecar.

### Board geometry

- `board_geometry_id=tft.board-grid.rectangular-4x7`, version 1.
- The board has 4 rows and 7 columns.
- Slot mapping is row-major: `row=slot/7;column=slot%7`.
- This is the current native rectangular slot convention only. It does **not** claim canonical TFT hex coordinates, adjacency, orientation or enemy-facing semantics.
- Bench and shop positions remain separate domains.

### Snapshot delivery

- Native state snapshot contract version is 2.
- Snapshot identity, observation and action masks remain atomically correlated by the existing Engine snapshot sequence and per-player decision sequences.
- The enriched structured records remain non-tensor metadata until a separately reviewed projection contract consumes them.
- Missing, empty, unknown, stale and not-applicable remain distinct; no synthetic physical item/component IDs, candidate IDs or event history are introduced.

## 5. Cross-component impact

Changes the native unit snapshot DTO, native snapshot producer, pybind serialization, Python wrapper validation, factory UUID issuance, API/wrapper/factory tests, producer coverage CSV and documentation. No action catalog/dimensions, action masks, Engine legality, rewards, PPO policy, Actor/Critic tensors, checkpoint format, Viewer or Overwolf behavior changes.

## 6. Objective validation

- Native API test verifies v2 contract and exact 4x7 geometry metadata.
- Native API test verifies per-unit trait membership is present as a typed list and active unit UUIDs are unique across all owners/locations in one snapshot.
- Existing movement test verifies the same UUID follows a physical unit across bench→board and board→board moves.
- Factory test verifies separate creations receive distinct UUIDs.
- Wrapper tests reject duplicate active UUIDs and malformed trait membership.
- CI must pass the relevant C++ and Python test workflows before this bounded delivery is considered validated.

## 7. Explicit limitations

This delivery does not prove every UnitInstance terminal lifecycle path (sale, merge, elimination and pool return) with a single integrated replay. It does not create physical item/component IDs, stable strategic candidate IDs, typed anti-loop event history, canonical hex coordinates, item-granted trait membership, or real GEP match identity. Shadow assessments and recommendations remain diagnostic-only. Issue #346 and Stage 1 remain open.
