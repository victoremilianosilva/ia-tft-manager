# Unit Instance, Shop Offer and Shared Pool Lifecycle Follow-up v1 — Draft

**Status:** source-backed lifecycle follow-up; documentation only.  
**Tracking:** [Issue #346](https://github.com/victoremilianosilva/ia-tft-manager/issues/346).  
**Base:** `new-arquiteture`.

## 1. Purpose and boundary

The earlier producer audit established that `UnitInstance::uuid` is generated by a seeded factory and repeats after a same-seed Engine reset. This follow-up traces the concrete ownership transitions, value-copy behavior, shop-offer lifecycle, elimination path, pool-count API and the tests that currently cover them.

This is not a runtime identity contract and does not authorize changing `UnitInstance`, the factory, shop, pool, pybind or PPO. It refines current producer evidence and records the remaining acceptance gaps.

## 2. Physical UnitInstance identity

### 2.1 Type and factory

- `UnitInstance` is a plain value struct with `champion_internal_id`, textual `champion_id`, `uuid`, `star` and an item vector. It declares no custom copy constructor, copy assignment, move constructor, move assignment or destructor (`cpp/include/lobby/TftEngine.hpp:118-145`). C++ therefore supplies ordinary value-copy/move behavior for its members; copying a UnitInstance copies its UUID string.
- `UnitInstanceFactory::create` validates the catalog ID, assigns the champion catalog references, calls `generate_uuid()` and initializes star to 1 (`cpp/src/lobby/UnitInstanceFactory.cpp:15-35`).
- `generate_uuid()` consumes two `std::mt19937_64` outputs, fills 16 bytes, sets version/variant bits and formats a UUID-shaped string (`cpp/src/lobby/UnitInstanceFactory.cpp:38-74`). The factory RNG is initialized only from its constructor seed.
- `TFTEngine::Impl` owns one factory shared across player initialization and shop generation, rather than a factory scoped per player (`cpp/src/lobby/TftEngine.cpp:688-695`; `cpp/src/lobby/TftEngine.cpp:1162-1235`).

**Disposition:** native per-object identifiers are produced, but raw UUID is not an accepted globally or cross-episode unique identity. No collision registry, Engine episode namespace or player namespace is attached to the value.

### 2.2 Copy and diagnostic snapshot semantics

- Board and bench decision-state construction reads the owned instances and creates `decision::UnitSnapshot` values, copying UUID/champion/star fields into a separate read-only decision representation (`cpp/src/lobby/TftEngine.cpp:733-785`).
- For a shop offer, the code first constructs a temporary `std::optional<UnitInstance>{*offer}`, which value-copies the offer, then converts it into `UnitSnapshot`. This is a diagnostic/decision snapshot copy, not a second owned shop or player unit (`cpp/src/lobby/TftEngine.cpp:776-785`).
- The value type itself does not prevent external callers or test hooks from copying a UnitInstance and thereby duplicating its UUID. The test-only `set_offer_for_testing` accepts a UnitInstance by value and moves it into an offer slot (`cpp/include/lobby/ShopEngine.hpp`; `cpp/src/lobby/ShopEngine.cpp:79-94`).

**Invariant:** a UUID copied into a snapshot is a reference to the same observed instance, not a new physical instance. A future structured contract must preserve that distinction and must not infer ownership from a copied diagnostic record.

## 3. Owned-instance lifecycle

| Transition | Source-backed behavior | Identity consequence |
|---|---|---|
| Initial player unit | Factory creates the starter and stores it in bench slot 0 | New factory UUID becomes the owned instance identifier |
| Shop draw | Shop draws a champion copy from UnitPool, then calls the shared factory | Offer carries a UnitInstance UUID; this is not a separate offer ID |
| Purchase | `take_unit` moves the offer out and clears the shop slot; PlayerEnv moves it into a free bench slot | UUID is preserved across shop → bench |
| Bench → board | Move assignment or swap of `optional<UnitInstance>` values | UUID moves with the physical value |
| Board move/swap | Move assignment or swap of board optionals | UUID is preserved; slot is not identity |
| Automatic 3-copy merge | Purchased unit remains the destination; two same-champion/same-star instances are reset; equipped items are transferred from consumed UUIDs to the surviving UUID; surviving star increments | Purchased UUID survives; two consumed UUIDs cease to identify owned units |
| Sale | Bench unit's star-copy count is returned to UnitPool; equipped items are returned to inventory; bench optional is reset | Sold UUID leaves active ownership; recent-purchase history may retain it as historical evidence |
| Elimination | Shop offers are returned; board/bench star-copy counts are returned to pool; board/bench optionals are reset | Owned UUIDs leave active board/bench ownership |
| Episode reset | Shops are returned/destroyed, pool is reset, factory is recreated from `impl_->seed`, then players are initialized | UUID generation stream restarts from the same seed |

Evidence:
- Initial creation/reset: `cpp/src/lobby/TftEngine.cpp:1162-1235`, `cpp/src/lobby/TftEngine.cpp:6170-6210`.
- Purchase and merge: `cpp/src/lobby/TftEngine.cpp:5046-5089`.
- Bench/board move and swap: `cpp/src/lobby/TftEngine.cpp:5219-5244`, `cpp/src/lobby/TftEngine.cpp:5317-5329`.
- Sale: `cpp/src/lobby/TftEngine.cpp:5605-5628`.
- Elimination: `cpp/src/lobby/TftEngine.cpp:4570-4603`.

### 3.1 Reset collision is confirmed

`TFTEngine::reset()` increments `episode_id`, but recreates `UnitInstanceFactory` with `impl_->seed`, not a seed incorporating the new episode ID (`cpp/src/lobby/TftEngine.cpp:6170-6210`). `initialize_players()` creates the starting bench units through that factory (`cpp/src/lobby/TftEngine.cpp:1162-1235`). Therefore, the first generated UUID after a reset with the same Engine seed repeats. The numeric episode ID does not namespace the UUID.

The factory is shared by all eight players during one episode, so generated values are sequential within that Engine instance, not independently player-scoped. No registry rejects duplicate UUID values from copies or external test hooks.

### 3.2 Elimination/item ownership edge

The elimination routine returns champion copies and clears board/bench optionals, but it does not call an ItemEngine per-unit equipment-return operation. The ItemEngine is reset during the next player initialization/episode reset, not in `return_eliminated_player_units` (`cpp/src/lobby/TftEngine.cpp:4570-4587`; `cpp/src/lobby/TftEngine.cpp:1204-1218`).

This proves that the elimination path does not explicitly reconcile equipped-item ownership before clearing units. Whether the retained equipment map is observable or causes any later semantic effect for an eliminated player needs a dedicated follow-up; do not infer that equipment was returned to inventory.

## 4. Shop offer identity

- Shop has five optional UnitInstance slots and no `offer_id`, offer revision or reroll-generation field (`cpp/include/lobby/ShopEngine.hpp`).
- `draw()` obtains a champion copy from UnitPool and creates a fresh UnitInstance through the shared factory (`cpp/src/lobby/ShopEngine.cpp:12-20`).
- `roll()` returns previous offers before drawing replacements; `take_unit()` moves an offer out and clears the slot (`cpp/src/lobby/ShopEngine.cpp:21-70`).
- The offer UUID identifies the temporary UnitInstance object only within the factory stream. It is not a stable shop-offer identity and is not scoped to player, shop snapshot, slot revision or decision sequence.

A future offer reference requires an explicit player/shop-snapshot/slot/revision envelope. No such record is produced today.

## 5. Shared champion pool: correction to prior coverage wording

A source-backed per-champion count producer does exist:

- `UnitPool::available(champion_internal_id)` returns the current remaining count; `initial_count` returns the original count; `take`, `give_back` and `reset` mutate/restore the shared counts (`cpp/include/lobby/UnitPool.hpp`; `cpp/src/lobby/UnitPool.cpp:12-45,61-140`).
- The pool is one shared lobby-level pool owned by `TFTEngine::Impl`, not a player-owned inventory (`cpp/src/lobby/TftEngine.cpp:688-695`).
- TFTEngine exposes `pool_available`, `pool_initial_count` and `pool_total_available` (`cpp/include/lobby/TftEngine.hpp:658-666`; `cpp/src/lobby/TftEngine.cpp:7352-7384`).
- Pybind exposes these as query methods (`cpp/bindings/tft_engine_bindings.cpp:927-929`).

**Correction:** the earlier coverage row saying no authoritative per-champion remaining-count producer exists was too broad. The Engine has an authoritative native query and a direct pybind query surface. What remains absent is a sequence-bound pool snapshot/entity in the observation/diagnostic payload and any PPO feature delivery. The count is queryable, but the query alone does not prove that a particular observation/action decision used that exact pool snapshot.

The pool's internal PvE component-drop pool is a separate resource and must not be confused with shared champion availability.

## 8. Architecture reconstruction review

1. **Prior problem:** the prior audit proved UUID generation and same-seed reset repetition but did not fully distinguish value copies, ownership transfers, shop-offer identity, elimination cleanup and the separate shared champion pool query API.
2. **Technical justification:** a UUID string can be copied without creating a new owned unit; a shop slot can be reused without preserving offer identity; an internal pool query can be authoritative without being correlated to a policy observation.
3. **New responsibility:** this follow-up owns the current UnitInstance/shop/pool lifecycle evidence and corrects the pool-availability producer classification; it does not establish a future identity contract.
4. **Contract and invariants:** raw UUID is not cross-episode identity; champion ID and slot are not physical identity; moves preserve values; merge consumes two identities; diagnostic copies are not ownership; pool count is shared-lobby state and query-only; masks remain separate legality inputs.
5. **Cross-component impacts:** UnitInstance, UnitInstanceFactory, PlayerEnv, ShopEngine, UnitPool, ItemEngine, TFTEngine reset/elimination, pybind, Python wrapper, schema entity manifest, PPO observation, replay and checkpoint lineage.
6. **Objective validation:** every lifecycle transition in the table is tied to native source lines; four targeted tests are mapped to proven and unproven behaviors; the shared pool producer is traced through TFTEngine and pybind; no runtime/schema/tensor/PPO/reward/mask/training/checkpoint/Viewer changes are made.

Issue #346 remains open. This document does not approve Gate 8 or any runtime implementation.
