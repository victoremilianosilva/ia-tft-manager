# Viewer–Engine Session Correlation Source Audit v1 — Draft

**Status:** source-backed static audit; documentation only.  
**Tracking:** [Issue #346](https://github.com/victoremilianosilva/ia-tft-manager/issues/346); Gate 7 correlation requirements in [Strategic Shadow Integrated Replay Contract v1](strategic-shadow-integrated-replay-contract.v1.draft.md).  
**Base:** `new-arquiteture`.  
**Primary source:** `viewer/session.py` (`ViewerSession`).

## 1. Purpose

Trace the Viewer session identity and event sequence through the current Viewer implementation, reconcile the Engine episode reference attached to Composition Intelligence diagnostics, and distinguish this diagnostic correlation from PPO transition identity.

This is an audit only. It does not change Viewer, Engine, wrapper, masks, PPO, replay, or runtime behavior.

## 2. Viewer session identity lifecycle

### 2.1 Creation

`ViewerSession.load_checkpoint()` calls `close()` before constructing a new session, then:
- creates a native `CppTFTLobbyWrapper` and calls `reset(seed)`;
- creates `self.match_id = str(uuid.uuid4())`;
- initializes current masks and public/audit snapshots;
- resets `step_count` to zero and resets the session event sequence through the preceding `close()`;
- optionally creates the session directory and writes `metadata.json`.

The Viewer UUID is therefore generated by the Python Viewer session, not by TFTEngine. It is not interchangeable with native `episode_id`.

### 2.2 Event sequence

`ViewerSession._emit()` increments `self._sequence` and writes:
- Viewer `match_id`;
- monotonic `sequence_id`;
- timestamp;
- current `step_count`, round and stage;
- event type, checkpoint hash and payload.

The sequence is a Viewer event-order counter. It is not a native Engine decision sequence, a Composition Intelligence evaluation sequence, or a PPO rollout index.

The Viewer emits distinct `decision_batch` and `step_completed` events. The former records proposed actions and policy diagnostics before the native step; the latter records submitted actions, rewards, Engine events, and before/after snapshots. These event types are useful for session navigation and audit, but the inspected event envelope does not establish a canonical decision ID shared with Engine masks, native action resolution and PPO rollout storage.

## 3. Composition Intelligence diagnostic correlation

When `_persist_composition_diagnostics()` writes native diagnostic JSONL records, it:
1. reads the native diagnostic line;
2. preserves the native `engine_match_id` value;
3. replaces the record's top-level `match_id` with the Viewer UUID;
4. adds a `correlation` object containing Viewer `match_id`, source label, native `engine_match_id`, player, round, timestamp, diagnostic sequence and composition identity/version.

This is an explicit two-namespace mapping for the Composition Intelligence diagnostic records that pass through this persistence method. It is not proof that every Viewer event, player log, Unified sidecar record, native observation, mask or PPO transition carries the same mapping.

The metadata declares `match_id_source = ViewerSession.match_id` and a correlation-envelope version for Composition Intelligence diagnostics. It does not itself declare a native Engine episode identity for the session as a whole.

## 4. Confirmed completeness defect

The current `identity_complete` predicate checks only:
- `player_id` is an `int`;
- `round` is an `int`;
- `sequence` is an `int`.

It does **not** require `engine_match_id` to be present, numeric, or otherwise valid. Consequently, a diagnostic record can be labeled identity-complete while lacking the Engine episode reference required to establish Viewer↔Engine correlation.

There is also a Python type nuance: `bool` is a subclass of `int`, so `isinstance(value, int)` accepts boolean values for these three fields. The current predicate does not explicitly reject booleans. This is a validation weakness independent of the missing Engine ID.

The timestamp is tracked separately through `timestamp_available`; it is not part of the current `identity_complete` predicate. This audit does not recommend making wall-clock timestamp a required identity component.

## 5. Scope and delivery boundaries

| Surface | What the inspected implementation establishes | What it does not establish |
|---|---|---|
| Viewer session | UUID `match_id` generated on load; session-local event sequence | Globally unique Engine-instance scope |
| Viewer events | Viewer UUID and event-order sequence | Shared native decision identity |
| Composition Intelligence JSONL | Explicit Viewer UUID + native `engine_match_id` mapping for persisted records | Coverage of every diagnostic/session artifact |
| Unified strategic sidecar | Native Engine match ID and its own recorder sequence, as described by the current replay audit | Viewer UUID embedded directly in each sidecar record |
| Viewer replay | Validates schema and monotonic unique `sequence_id`, then navigates recorded events | Re-execution of Engine, policy, masks or Shadow |
| PPO rollout | Existing audit finds observations and masks in separate tensors, without match/episode/player/round/decision identity | Join from an individual rollout transition to Viewer/Engine diagnostic records |

The PPO and wrapper conclusions above are cross-references to the source-backed [Current Replay, Correlation and Evaluation Gap Audit](current-replay-correlation-evaluation-gap-audit.v1.draft.md); this Viewer source audit does not claim to have independently re-traced every Python wrapper and rollout callsite.

## 6. Required contract corrections and post-Gate-8 proof

1. A Viewer↔Engine correlation record may be marked complete only when both Viewer session identity and a validated native Engine episode identity are present, together with the required player/round/source-sequence fields.
2. Integer validation for identity fields must reject booleans explicitly and enforce the field's actual domain/range.
3. Keep Viewer event sequence, Engine episode ID, Composition Intelligence sequence, recorder sequence and PPO rollout index as separate namespaces.
4. Preserve the native Engine ID before assigning the Viewer UUID to the persisted diagnostic record's top-level `match_id`; field names must not imply the two IDs are aliases.
5. Define how the Viewer session is bound to a specific Engine object scope and episode, including reset behavior and any Engine reconstruction.
6. Extend correlation beyond Composition Intelligence diagnostics only through explicit, validated envelope propagation; do not infer coverage from matching timestamps, adjacent records or equal numeric IDs.
7. Bind observation and mask snapshots to the same decision identity before policy evaluation, and carry that identity through action, reward and rollout storage.
8. Add negative fixtures for missing/invalid Engine ID, boolean IDs/sequences, mismatched Viewer↔Engine mapping, Engine reset, multiple Engine objects, duplicate event sequence and session reload.
9. Keep Viewer log playback classified as log playback; integrated replay must re-execute or deterministically reconstruct the required Engine/Shadow/PPO chain.

No runtime fix is proposed or authorized by this document. The exact implementation and acceptance criteria remain post-Gate-8 work.

## 7. Architecture reconstruction review

1. **Prior problem:** the existing audit identified that `identity_complete` omitted `engine_match_id`, but the Viewer implementation's session/event lifecycle and the precise validation predicate needed a direct source trace.
2. **Technical justification:** Viewer UUID, native Engine episode ID and Viewer event sequence are produced by different owners and have different scopes; Python's `bool`-is-an-`int` behavior also weakens the current type predicate.
3. **New responsibility:** this note owns the source-backed Viewer session lifecycle, event-order semantics, diagnostic correlation mapping and current completeness-predicate findings.
4. **Contract and invariants:** Viewer UUID is not Engine episode ID; event sequence is not decision sequence; diagnostic correlation is explicit and partial; complete correlation requires a valid Engine episode reference; booleans are not valid integer identity values.
5. **Cross-component impacts:** `viewer/session.py`, native `TFTEngine::episode_id`, Composition Intelligence diagnostics, Unified sidecar, Viewer replay, wrapper observation/mask delivery, PPO rollout identity and Gate 7 replay.
6. **Objective validation:** the Viewer constructor/load/close lifecycle, UUID creation, event emission, diagnostic envelope and exact completeness predicate are traced; the missing Engine-ID and boolean-type defects are recorded; no runtime or tensor change is made.


## 6. Native wrapper and PPO rollout source trace

The current Python/native boundary reinforces the correlation gap:

- `CppTFTLobbyWrapper.reset()` calls native `_engine.reset(seed)` but returns only `result["observations"]` as a float32 array. Any native episode identity in the reset result is not propagated by this wrapper return value.
- `CppTFTLobbyWrapper.step()` calls native `_engine.step(...)`, then constructs a restricted `info` dictionary from players, round, stage, lobby completion, events and reward components. It returns observations, rewards, done and this info; it does not propagate an Engine episode ID or typed decision identity.
- `CppTFTLobbyWrapper.get_action_masks()` is a separate native call. The wrapper does not attach a match/episode/decision identity to the returned mask object.
- `LobbyVectorEnv.reset()` stacks only the observation arrays. `LobbyVectorEnv.step()` stacks observations/rewards/dones and forwards per-lobby info; it does not introduce an identity envelope.
- `RolloutBuffer` allocates and stores observations, actions, log probabilities, rewards, dones, values, validity and mask tensors. Its `add()` contract has no match ID, Engine episode ID, player ID, round, decision ID or typed producer-sequence argument/field.
- The existing PPO audit separately establishes that Trainer obtains masks through `env_method("get_action_masks")`, stores them alongside the transition, and uses them for Actor policy evaluation; this does not prove that the mask belongs to the exact observation/decision by identity.

This confirms a loss of native episode identity at the Python wrapper boundary and absence of transition identity in the current rollout data model. It is not merely a Viewer logging limitation.

## 7. Cross-component findings

| Boundary | Current behavior | Missing proof |
|---|---|---|
| TFTEngine reset → wrapper reset | Native result is reduced to observations | Episode ID not returned to Python caller |
| TFTEngine step → wrapper step | Native result reduced to observations/rewards/dones and selected info | Episode/decision identity not retained in info |
| Native masks → Trainer | Separate `get_action_masks()` call | No identity binding to observation |
| Vector environment → Trainer | Arrays and per-lobby info | No stable Engine/session/player/round envelope |
| Trainer → RolloutBuffer | Tensor transition and masks | No typed source identity in stored transition |
| Viewer → Composition diagnostics | Viewer UUID plus native Engine ID on that diagnostic path | Not propagated to every event/observation/mask/rollout |

The required identity propagation must be designed as one explicit contract across these boundaries after Gate 8. Do not solve this by copying the Viewer UUID into a field named `engine_match_id`, by using the rollout tensor index as a decision ID, or by assuming separately fetched masks are current because they were fetched immediately before inference.

## 8. Updated post-Gate-8 proof

In addition to the Viewer-specific tests above, the integrated acceptance must:
1. preserve native Engine scope and episode identity through wrapper reset and step results;
2. bind each observation and mask snapshot to the same immutable decision identity;
3. preserve identity through vectorization, action selection, reward attribution and RolloutBuffer storage/minibatch indexing;
4. prove per-player identity under multi-lobby flattening and terminal lobby reset;
5. reject missing, stale, mismatched or cross-episode masks and transitions;
6. demonstrate joins from a rollout transition to native state, Viewer diagnostics and the correct Engine episode without relying on timestamps or array adjacency.

No implementation is performed here.

## 9. Architecture reconstruction review

1. **Prior problem:** the Viewer correlation predicate was known to be incomplete, but the native wrapper and rollout boundary also needed a direct source trace to establish where Engine episode identity is dropped.
2. **Technical justification:** wrapper reset/step expose arrays and selected metadata, while RolloutBuffer persists tensors without identity fields; masks are fetched separately and have no decision binding.
3. **New responsibility:** this document now owns the source-backed Viewer session lifecycle, diagnostic correlation predicate, wrapper identity boundary and rollout identity gap.
4. **Contract and invariants:** preserve Viewer and Engine namespaces; never infer mask/observation pairing from call order; never infer transition identity from tensor position; keep every player/lobby/episode scope explicit.
5. **Cross-component impacts:** `viewer/session.py`, `cpp_lobby_env.py`, `vector_lobby_env.py`, `trainer.py`, `rollout.py`, TFTEngine native reset/step results, masks, replay and PPO.
6. **Objective validation:** Viewer UUID/event lifecycle, diagnostic envelope predicate, wrapper reset/step return shape, vector adapter and RolloutBuffer storage fields are traced; missing identity propagation is explicit; no runtime or tensor change is made.

Issue #346 remains open. Gate 7 executable acceptance remains pending. Gate 8 remains blocked.

## Runtime reconciliation — PR #497

The sections above preserve the original source-audit findings. The following changes supersede only the Viewer projection/persistence behavior described there; they do not claim a shared PPO/native decision identity.

**Prior problem:** ViewerSession enriched each native audit player with a StrategyInfo snapshot, and PlayerCard, player details and composition dialog treated those fields as current strategic state. The diagnostic sidecar cursor also did not reset when the native episode changed.

**Technical rationale:** Composition Intelligence diagnostics are the canonical read-only Shadow producer. Viewer UI and current logs should consume that producer directly, while historical StrategyInfo fields remain clearly marked as compatibility-only.

**Owner and boundaries:** TFTEngine/CompositionIntelligencePlayerRuntime own the diagnostic records. ViewerSession attaches the latest per-player diagnostic and persists it. viewer/shadow_projection.py is a pure read-only projection. PlayerJsonLogWriter preserves old fields only as explicitly labelled compatibility data.

**Contract and invariants:** PlayerCard, player dialog, selected-player panel and composition dialog read composition_decision, lineup_plan.selected_board, unit_intentions and action_recommendation from shadow_composition. No current UI fallback to strategy_info remains in viewer/main.py. Sidecar append cursor is scoped by native episode_id and resets when the episode changes. Historical logs remain readable; no legacy values are promoted to canonical Shadow state.

**Impacts:** viewer/session.py, viewer/main.py, viewer/player_logs.py, viewer/shadow_projection.py and focused Viewer tests. No policy, PPO observation, action, mask or execution behavior changes.

**Validation:** tests/test_viewer_session_shadow_projection.py verifies that StrategyInfo is not requested and that the latest Shadow record is attached; it also verifies sidecar append across episode reset. tests/test_viewer_shadow_projection.py verifies pure canonical projections and unavailable-state behavior. tests/test_viewer_shadow_planning_logs.py verifies compatibility labels and persisted Shadow payload.

**Remaining limitations:** Viewer↔Engine session identity correlation remains a separate namespace mapping, not a canonical PPO decision ID. The UI displays the current diagnostic selected_board and unit intentions; it does not imply that a Shadow recommendation was executed or that a proposed position is an authoritative Engine destination.
