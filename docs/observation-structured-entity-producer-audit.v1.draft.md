## Physical unit identity

### Native declaration

`cpp/include/lobby/TftEngine.hpp` declares `UnitInstance` with:

- `champion_internal_id`: internal catalog reference;
- `champion_id`: champion API/catalog identity;
- `uuid`: intended identity of an individual copy;
- `star`: mutable star state;
- `items`: equipment attached to that copy.

The declaration comment says effective UUID generation will be implemented later. That comment is stale relative to the implementation: a producer exists in `UnitInstanceFactory`. The `is_valid()` predicate requires a non-empty UUID, but the predicate itself is not a generation or uniqueness guarantee.

### Authoritative creation path found

- `cpp/include/lobby/UnitInstanceFactory.hpp` declares `UnitInstanceFactory::create()` and private `generate_uuid()`.
- `cpp/src/lobby/UnitInstanceFactory.cpp::UnitInstanceFactory::create()` resolves the champion definition, fills catalog identity, calls `generate_uuid()`, and returns a new one-star `UnitInstance`.
- `generate_uuid()` consumes two `std::mt19937_64` outputs to fill 16 bytes, sets UUID version/variant bits, and formats a 36-character UUID string.
- The factory RNG is initialized from the constructor seed. `TFTEngine::Impl` owns one factory shared by player initialization and shop generation; it is not a separate factory per player.
- The initial player setup creates the starting unit through this factory. Shop draws also call the same factory after taking a champion copy from `UnitPool`.

**Finding:** UUID generation is implemented and generated values are non-empty for successful `create()` calls. The header comment should be corrected in a later source-change task, but no runtime edit is made in this audit.

### Uniqueness and scope

The factory does not maintain a registry/set of issued UUIDs and does not check for collisions. The UUID bytes are generated by a seeded pseudorandom engine; this is deterministic, not an OS-random UUID service.

More importantly, `TFTEngine::reset()` reconstructs `UnitInstanceFactory` with `impl_->seed` again. The first factory-generated UUID after reset is therefore repeated for the first created unit (the initial unit creation path), because the RNG is restarted from the same seed. A second Engine initialized with the same seed has the same deterministic first UUID as well.

Consequences:

- UUID is **not globally unique across episodes or Engine instances**.
- UUID has no encoded `engine_match_id` or `player_id` scope.
- Within one factory stream, IDs are generated sequentially, but the code does not formally enforce uniqueness or detect collision.
- The native UUID cannot be used as a standalone cross-match identity. Any future identity must be scoped by an explicit episode/match and player identity, or generation must be changed and validated.

### Ownership and lifecycle evidence

Source inspection establishes the following object behavior:

| Lifecycle operation | Source path | Identity effect | Evidence boundary |
|---|---|---|---|
| Create starting unit | `TftEngine.cpp::initialize_players()` → `unit_factory->create()` | New UUID assigned | Factory-local deterministic identity |
| Create shop offer | `ShopEngine.cpp::draw()` → `factory_.create()` | New UUID assigned per successful offer creation | Offer has no separate stable offer ID |
| Purchase offer | `ShopEngine::take_unit()` then purchase handling in `TftEngine.cpp` | Optional `UnitInstance` is moved out of shop into owned board/bench state | UUID is carried with the object |
| Board/bench movement | Player action handling swaps/moves `optional<UnitInstance>` values | Existing UUID moves with the instance | No regeneration in the inspected move path |
| Upgrade/merge | Purchase merge path selects three same-champion/same-star copies; two consumed instances are removed; purchased instance gets incremented star | Purchased instance UUID survives; consumed UUIDs cease to represent owned instances | Equipped items are transferred from consumed UUIDs to the surviving UUID |
| Sale | Sell path captures `unit.uuid`, returns pool copies and removes the owned unit | Sold UUID leaves active ownership | Recent-purchase history may retain the old UUID as temporal evidence |
| Engine reset | `TFTEngine::reset()` recreates factory using the same seed and reinitializes players | UUID sequence restarts; first generated identity repeats | Cross-episode collision is confirmed |

This establishes object-transfer continuity for the inspected paths, not a complete formal lifecycle contract. Copy construction/assignment sites, all external test hooks, duplicate detection, and every sale/elimination/reset edge still require a repository-wide test and callsite audit.

### Current consumers

`cpp/src/lobby/TftEngine.cpp` reads UUID for item profiles, ItemEngine equipped lookups, movement/purchase history correlation, item action targets, merge equipment transfer and diagnostic snapshots. Some consumers explicitly skip or condition behavior when UUID is empty. These consumers do not turn the UUID into a cross-match-safe identity.

### Status

**UNVERIFIED as canonical physical identity**

The producer is now located, and same-episode object transfer is partially evidenced. The identity still fails the required cross-episode scope guarantee and lacks a complete formal uniqueness/lifecycle contract.

Remaining proof required:

1. repository-wide enumeration of every `UnitInstance` construction, copy, assignment and destruction path;
2. collision behavior and uniqueness enforcement within one Engine episode;
3. player/match scoping and reset-safe identity;
4. lifecycle regression tests for purchase, board/bench movement, merge, sale, elimination and consecutive matches;
5. exact correlation of identity with the relevant snapshot sequence.

### Schema reconciliation

Schema v2 currently requires `unit.instance_id`; the native field is `UnitInstance::uuid`. A semantic mapping may eventually be appropriate, but a raw alias is not sufficient: native UUID currently repeats across episodes when the seed is reused and carries no player/match namespace.

Do not map `instance_id = uuid` as a globally stable identity. A future versioned correction must define a composite/scoped identity or change the producer and prove its lifecycle before the schema field is accepted.


## Board and bench slot producers

### Native representation

`TftEngine.hpp` defines fixed native capacities:

- board: `kBoardSlots = 28`;
- bench: `kBenchSlots = 9`;
- shop: `kShopSlots = 5`.

The player state stores board and bench as fixed arrays of `std::optional<UnitInstance>`. The optional value distinguishes an occupied slot from an observed empty slot in the native in-memory state. The audit snapshot preserves the fixed arrays and emits one `AuditUnitSnapshot` per slot; `occupied=false` represents an empty slot, while `occupied=true` carries champion, UUID, star, cost and item catalog IDs.

### Slot identity and topology

- A board slot is identified by its array index in the 28-element board domain; a bench slot is identified by its index in the 9-element bench domain.
- The observation builder preserves these positions: it emits five values for each board slot and each bench slot, advancing across empty slots rather than compacting occupied units.
- Existing board logic uses `slot / 7` for a coarse row classification (four groups of seven). This is not enough to define TFT's canonical hex coordinates, orientation, adjacency or front/back geometry.
- Moving or swapping a unit changes its slot relationship but moves/swaps the `optional<UnitInstance>` itself; the unit UUID follows the instance. Slot identity and physical unit identity are therefore separate.
- The audit snapshot contains round and stage but no typed per-entity source sequence or explicit episode/match identity. The fixed slot arrays prove positional indexing, not exact decision-sequence correlation.

### Status

**NATIVE SLOT INDEX AND OCCUPANCY OBSERVED; SPATIAL MAPPING AND SEQUENCE CORRELATION UNVERIFIED**

The fixed slot index and empty/occupied state are native. Canonical coordinate/orientation mapping, adjacency semantics, player/match/sequence envelope and delivery into PPO as structured entities are not established. The PPO tensor contains slot-aligned numeric features but no physical UUID per slot.

## Shop offer producer and lifecycle

### Native creation and replacement path

- `ShopEngine::draw(cost)` asks `UnitPool::draw_by_cost` for an available champion copy and then calls the shared `UnitInstanceFactory::create()`.
- `ShopEngine::roll(level, force)` returns the previous offers to the shared pool, then fills the five fixed offer slots. A locked shop is not rerolled unless forced.
- `reroll(level)` delegates to `roll(level, true)`.
- `take_unit(slot)` moves the `UnitInstance` out of the offer slot and clears that slot. The purchase path then moves that instance to the player's bench; if an automatic merge occurs, the purchased instance is the surviving identity.
- A shop offer's champion cost is read from the champion catalog definition at purchase/evaluation time. `ShopEngine` does not maintain a separately versioned price field on the offer.
- The test hooks `set_offer_for_testing` and `set_next_roll_for_testing` are fixture mechanisms, not independent production identity authorities.

### Identity distinction

The offer reuses the UUID of the temporary `UnitInstance` created for that offer. No separate `offer_id`, offer revision, or reroll-generation token is produced by `ShopEngine`. Slot index alone is not a stable offer identity because reroll replaces the contents of the same slot. When an offer is purchased, its UnitInstance UUID continues with the owned unit; when rerolled/returned, the offer instance is discarded and the champion copy returns to the pool.

Therefore, the UUID may identify the temporary unit object within the factory stream, but it does not by itself provide a stable shop-offer identity. A future offer key must be scoped to player, exact shop snapshot/decision sequence, slot and offer revision; none of those revisions is currently emitted as a complete typed envelope.

### Current delivery

The native audit snapshot exposes five fixed shop entries with `occupied`, champion ID, UUID, star and cost. The PPO observation builder emits five slot-aligned numeric records, but does not include a typed offer identity, offer revision, or UUID in the flat vector. The audit snapshot is diagnostic and has no typed source-sequence envelope.

### Status

**NATIVE OFFER CONTENT AND SLOT OBSERVED; OFFER IDENTITY/REVISION AND PPO STRUCTURED DELIVERY NOT PRODUCED**

The five slot positions, occupied state, champion catalog identity and catalog-derived cost are observable. A stable offer ID, explicit offer revision/reroll sequence, and exact decision-sequence correlation are not produced in the inspected path. Do not infer offer identity from champion ID, slot index or the temporary unit UUID.

## Current Engine-to-Python and PPO delivery boundary

The binding `cpp/bindings/tft_engine_bindings.cpp` exposes UUID through `TFTEngine::get_audit_snapshot()`: each audit unit dictionary contains `occupied`, `champion_id`, `uuid`, `star` and `cost`. This is a diagnostic/audit sidecar.

The same binding's reset/step dictionaries expose flat `observations`, `action_masks`, episode/round metadata and other step results. They do not include structured unit UUID records in the PPO observation payload. `TFTEngine::Impl::build_observations()` emits a flat numeric vector and does not serialize a lossless entity record with UUID, field-level provenance and typed source sequence.

Therefore:

- UUID is exposed to Python through the diagnostic audit snapshot API;
- UUID is **not established as part of the trainer's observation tensor or rollout transition**;
- the audit snapshot itself has round/stage/player information but no typed per-entity source-sequence envelope proving correlation to the PPO observation/masks;
- diagnostic availability must not be described as PPO delivery.

## Architecture reconstruction review

1. **Prior problem:** the structured entity contract assumed `instance_id` without proving a native producer or lifecycle.
2. **Technical rationale:** projection identity must reflect actual ownership and episode scope; a seeded UUID that repeats after reset can silently join different physical units in replay or diagnostics.
3. **New responsibility:** this slice records producer and lifecycle evidence; schema acceptance remains dependent on identity scope and delivery proof.
4. **Contracts/invariants:** no champion/slot substitute; no standalone cross-match UUID; schema fields are not runtime evidence; diagnostic delivery is not PPO delivery.
5. **Cross-component impact:** UnitInstance, UnitInstanceFactory, PlayerEnv, ShopEngine, UnitPool, ItemEngine, board/bench transfer, pybind, Python wrapper, PPO rollout, replay and checkpoint lineage.
6. **Objective validation:** test UUID generation, within-episode uniqueness, reset collision, movement stability, merge/sale semantics, match/player scoping and Python exposure before accepting the field.
