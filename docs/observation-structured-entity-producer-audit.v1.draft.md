# Structured Entity Producer Evidence Audit — Identity Slice v1 (Draft)

**Status:** partial source audit; not runtime-approved. Full coverage tracked by [#346](https://github.com/victoremilianosilva/ia-tft-manager/issues/346).

## Scope of this slice

This document records source facts verified in the current `new-arquiteture` branch. It does not claim that all 17 entity kinds have been audited.

## Physical unit identity

### Native declaration

`cpp/include/lobby/TftEngine.hpp` declares `UnitInstance` with:

- `champion_internal_id`: internal catalog reference;
- `champion_id`: champion API/catalog identity;
- `uuid`: intended identity of an individual copy;
- `star`: mutable star state;
- `items`: equipment attached to that copy.

The declaration comment says effective UUID generation will be implemented later. That comment is stale relative to the implementation: a producer exists in `UnitInstanceFactory`. The `is_valid()` predicate requires a non-empty UUID, but the predicate itself is not a generation or uniqueness guarantee.

### Authoritative creation path found

- `cpp/include/lobby/UnitInstanceFactory.hpp` declares `UnitInstanceFactory::create()` and private `generate_uuid()`.
- `cpp/src/lobby/UnitInstanceFactory.cpp::UnitInstanceFactory::create()` resolves the champion definition, fills catalog identity, calls `generate_uuid()`, and returns a new one-star `UnitInstance`.
- `generate_uuid()` consumes two `std::mt19937_64` outputs to fill 16 bytes, sets UUID version/variant bits, and formats a 36-character UUID string.
- The factory RNG is initialized from the constructor seed. `TFTEngine::Impl` owns one factory shared by player initialization and shop generation; it is not a separate factory per player.
- The initial player setup creates the starting unit through this factory. Shop draws also call the same factory after taking a champion copy from `UnitPool`.

**Finding:** UUID generation is implemented and generated values are non-empty for successful `create()` calls. The header comment should be corrected in a later source-change task, but no runtime edit is made in this audit.

### Uniqueness and scope

The factory does not maintain a registry/set of issued UUIDs and does not check for collisions. The UUID bytes are generated by a seeded pseudorandom engine; this is deterministic, not an OS-random UUID service.

More importantly, `TFTEngine::reset()` reconstructs `UnitInstanceFactory` with `impl_->seed` again. The first factory-generated UUID after reset is therefore repeated for the first created unit (the initial unit creation path), because the RNG is restarted from the same seed. A second Engine initialized with the same seed has the same deterministic first UUID as well.

Consequences:

- UUID is **not globally unique across episodes or Engine instances**.
- UUID has no encoded `engine_match_id` or `player_id` scope.
- Within one factory stream, IDs are generated sequentially, but the code does not formally enforce uniqueness or detect collision.
- The native UUID cannot be used as a standalone cross-match identity. Any future identity must be scoped by an explicit episode/match and player identity, or generation must be changed and validated.

### Ownership and lifecycle evidence

Source inspection establishes the following object behavior:

| Lifecycle operation | Source path | Identity effect | Evidence boundary |
|---|---|---|---|
| Create starting unit | `TftEngine.cpp::initialize_players()` → `unit_factory->create()` | New UUID assigned | Factory-local deterministic identity |
| Create shop offer | `ShopEngine.cpp::draw()` → `factory_.create()` | New UUID assigned per successful offer creation | Offer has no separate stable offer ID |
| Purchase offer | `ShopEngine::take_unit()` then purchase handling in `TftEngine.cpp` | Optional `UnitInstance` is moved out of shop into owned board/bench state | UUID is carried with the object |
| Board/bench movement | Player action handling swaps/moves `optional<UnitInstance>` values | Existing UUID moves with the instance | No regeneration in the inspected move path |
| Upgrade/merge | Purchase merge path selects three same-champion/same-star copies; two consumed instances are removed; purchased instance gets incremented star | Purchased instance UUID survives; consumed UUIDs cease to represent owned instances | Equipped items are transferred from consumed UUIDs to the surviving UUID |
| Sale | Sell path captures `unit.uuid`, returns pool copies and removes the owned unit | Sold UUID leaves active ownership | Recent-purchase history may retain the old UUID as temporal evidence |
| Engine reset | `TFTEngine::reset()` recreates factory using the same seed and reinitializes players | UUID sequence restarts; first generated identity repeats | Cross-episode collision is confirmed |

This establishes object-transfer continuity for the inspected paths, not a complete formal lifecycle contract. Copy construction/assignment sites, all external test hooks, duplicate detection, and every sale/elimination/reset edge still require a repository-wide test and callsite audit.

### Current consumers

`cpp/src/lobby/TftEngine.cpp` reads UUID for item profiles, ItemEngine equipped lookups, movement/purchase history correlation, item action targets, merge equipment transfer and diagnostic snapshots. Some consumers explicitly skip or condition behavior when UUID is empty. These consumers do not turn the UUID into a cross-match-safe identity.

### Status

**UNVERIFIED as canonical physical identity**

The producer is now located, and same-episode object transfer is partially evidenced. The identity still fails the required cross-episode scope guarantee and lacks a complete formal uniqueness/lifecycle contract.

Remaining proof required:

1. repository-wide enumeration of every `UnitInstance` construction, copy, assignment and destruction path;
2. collision behavior and uniqueness enforcement within one Engine episode;
3. player/match scoping and reset-safe identity;
4. lifecycle regression tests for purchase, board/bench movement, merge, sale, elimination and consecutive matches;
5. exact correlation of identity with the relevant snapshot sequence.

### Schema reconciliation

Schema v2 currently requires `unit.instance_id`; the native field is `UnitInstance::uuid`. A semantic mapping may eventually be appropriate, but a raw alias is not sufficient: native UUID currently repeats across episodes when the seed is reused and carries no player/match namespace.

Do not map `instance_id = uuid` as a globally stable identity. A future versioned correction must define a composite/scoped identity or change the producer and prove its lifecycle before the schema field is accepted.


## Board and bench slot producers

### Native representation

`TftEngine.hpp` defines fixed native capacities:

- board: `kBoardSlots = 28`;
- bench: `kBenchSlots = 9`;
- shop: `kShopSlots = 5`.

The player state stores board and bench as fixed arrays of `std::optional<UnitInstance>`. The optional value distinguishes an occupied slot from an observed empty slot in the native in-memory state. The audit snapshot preserves the fixed arrays and emits one `AuditUnitSnapshot` per slot; `occupied=false` represents an empty slot, while `occupied=true` carries champion, UUID, star, cost and item catalog IDs.

### Slot identity and topology

- A board slot is identified by its array index in the 28-element board domain; a bench slot is identified by its index in the 9-element bench domain.
- The observation builder preserves these positions: it emits five values for each board slot and each bench slot, advancing across empty slots rather than compacting occupied units.
- Existing board logic uses `slot / 7` for a coarse row classification (four groups of seven). This is not enough to define TFT's canonical hex coordinates, orientation, adjacency or front/back geometry.
- Moving or swapping a unit changes its slot relationship but moves/swaps the `optional<UnitInstance>` itself; the unit UUID follows the instance. Slot identity and physical unit identity are therefore separate.
- The audit snapshot contains round and stage but no typed per-entity source sequence or explicit episode/match identity. The fixed slot arrays prove positional indexing, not exact decision-sequence correlation.

### Status

**NATIVE SLOT INDEX AND OCCUPANCY OBSERVED; SPATIAL MAPPING AND SEQUENCE CORRELATION UNVERIFIED**

The fixed slot index and empty/occupied state are native. Canonical coordinate/orientation mapping, adjacency semantics, player/match/sequence envelope and delivery into PPO as structured entities are not established. The PPO tensor contains slot-aligned numeric features but no physical UUID per slot.

## Shop offer producer and lifecycle

### Native creation and replacement path

- `ShopEngine::draw(cost)` asks `UnitPool::draw_by_cost` for an available champion copy and then calls the shared `UnitInstanceFactory::create()`.
- `ShopEngine::roll(level, force)` returns the previous offers to the shared pool, then fills the five fixed offer slots. A locked shop is not rerolled unless forced.
- `reroll(level)` delegates to `roll(level, true)`.
- `take_unit(slot)` moves the `UnitInstance` out of the offer slot and clears that slot. The purchase path then moves that instance to the player's bench; if an automatic merge occurs, the purchased instance is the surviving identity.
- A shop offer's champion cost is read from the champion catalog definition at purchase/evaluation time. `ShopEngine` does not maintain a separately versioned price field on the offer.
- The test hooks `set_offer_for_testing` and `set_next_roll_for_testing` are fixture mechanisms, not independent production identity authorities.

### Identity distinction

The offer reuses the UUID of the temporary `UnitInstance` created for that offer. No separate `offer_id`, offer revision, or reroll-generation token is produced by `ShopEngine`. Slot index alone is not a stable offer identity because reroll replaces the contents of the same slot. When an offer is purchased, its UnitInstance UUID continues with the owned unit; when rerolled/returned, the offer instance is discarded and the champion copy returns to the pool.

Therefore, the UUID may identify the temporary unit object within the factory stream, but it does not by itself provide a stable shop-offer identity. A future offer key must be scoped to player, exact shop snapshot/decision sequence, slot and offer revision; none of those revisions is currently emitted as a complete typed envelope.

### Current delivery

The native audit snapshot exposes five fixed shop entries with `occupied`, champion ID, UUID, star and cost. The PPO observation builder emits five slot-aligned numeric records, but does not include a typed offer identity, offer revision, or UUID in the flat vector. The audit snapshot is diagnostic and has no typed source-sequence envelope.

### Status

**NATIVE OFFER CONTENT AND SLOT OBSERVED; OFFER IDENTITY/REVISION AND PPO STRUCTURED DELIVERY NOT PRODUCED**

The five slot positions, occupied state, champion catalog identity and catalog-derived cost are observable. A stable offer ID, explicit offer revision/reroll sequence, and exact decision-sequence correlation are not produced in the inspected path. Do not infer offer identity from champion ID, slot index or the temporary unit UUID.

The binding `cpp/bindings/tft_engine_bindings.cpp` exposes UUID through `TFTEngine::get_audit_snapshot()`: each audit unit dictionary contains `occupied`, `champion_id`, `uuid`, `star` and `cost`. This is a diagnostic/audit sidecar.

They do not include structured unit UUID records in the PPO observation payload. `TFTEngine::Impl::build_observations()` emits a flat numeric vector and does not serialize a lossless entity record with UUID, field-level provenance and typed source sequence.

Therefore:

- UUID is exposed to Python through the diagnostic audit snapshot API;
- UUID is **not established as part of the trainer's observation tensor or rollout transition**;
- the audit snapshot itself has round/stage/player information but no typed per-entity source-sequence envelope proving correlation to the PPO observation/masks;
- diagnostic availability must not be described as PPO delivery.

## Item, component and anvil producer audit — source-backed slice

**Audit status:** partial source audit for #346. Findings below describe the inspected native Engine path; they do not authorize runtime changes or projection layout.

### Item catalog identity versus physical item identity

**Native owners and paths**

- `cpp/include/items/ItemEngine.hpp::ItemDefinition` stores a catalog `id`, recipe component catalog IDs, normalized stats/effects and `unit_equipable`. `ItemCatalog.hpp::load_item_catalog()` loads the active-set catalog.
- `ItemEngine` stores loose components as `std::vector<std::string> components_`, completed inventory as `std::vector<std::string> inventory_`, and equipped catalog IDs as `std::unordered_map<std::string, std::vector<std::string>> equipped_` keyed by unit UUID.
- Adding, crafting, equipping, detaching and merge transfer move catalog ID strings between those containers. No physical item-instance object, generated item-instance ID, copy identity, or item-level creation sequence is produced.
- Repeated component IDs in the vector preserve multiplicity as repeated values, not independently identified component instances. Repeated completed-item IDs likewise represent copies without physical identity.
- `UnitInstance::items` is synchronized from ItemEngine equipment through `sync_unit_items_from_engine()`; it stores combat item definitions/catalog API names, not item-instance references.

**Ownership/lifecycle**

- Equip consumes one matching catalog ID from inventory and appends it to the target unit UUID's equipped list.
- Sale returns every catalog ID from the sold unit's equipped list to inventory before removing the unit.
- Merge transfers equipped catalog IDs from consumed unit UUIDs to the surviving purchased unit UUID; overflow beyond the three-item cap returns to inventory.
- Engine reset clears components, inventory, equipped mappings, queued anvils and metrics. No item-instance identity survives or needs to be correlated across reset because none is produced.

**Snapshot and PPO delivery**

- `TFTEngine::get_audit_snapshot()` exposes loose component IDs, inventory item IDs, component catalog IDs, and unit attachment catalog IDs (via `UnitInstance::items`). These are diagnostic snapshot values, not physical item-instance records.
- The pybind `get_audit_snapshot` dictionary forwards those arrays/strings. It does not expose an explicit item-instance identity or typed item-owner relationship.
- The live PPO observation is not this diagnostic JSON. `build_observations()` emits fixed numeric blocks: component counts by catalog position (count divided by six and clamped), up to nine inventory item semantic feature rows, catalog-derived recipe features, board/bench target features, inventory-to-target fit values, and recipe-to-target fit values.
- Consequently PPO receives item semantics and derived compatibility values, but not raw physical item IDs, item-instance IDs, per-copy provenance, or typed source-sequence records. The inventory's numeric row position is a transient slot in the current vector, not a persistent item identity.
- The target-fit blocks are estimated/heuristic values from `ItemFitCache`; they must retain formula/provenance/uncertainty and must not be represented as observed facts.

**Disposition:** `item_catalog_entry` is native catalog metadata; `item_instance` is **not produced**. The schema's future `item_instance_id` cannot be populated from current catalog strings. A versioned producer/contract change is required before lossless item-instance projection.

### Component inventory

- The authoritative live component state is a vector of catalog IDs in `ItemEngine::components_`; duplicate IDs are separate owned copies by multiplicity only.
- PvE component drops are drawn from `Set18ComponentPool` and added through `ItemEngine::add_component()`. The pool's remaining count is internal loot-generation state; it is not a player-owned component-instance identity or shared champion-pool availability.
- The audit snapshot exposes the component ID vector. The PPO observation aggregates it into one count per catalog component, preserving multiplicity only as a count and applying `clamp(count / 6, 0, 1)`.
- No component instance ID, acquisition event ID, owner transition record or per-copy sequence is produced. Catalog order determines the current numeric feature positions and therefore requires catalog fingerprint/order binding.

**Disposition:** component catalog identity and aggregate counts are native; physical component instances are **not produced**. A repeated string is not an instance identifier. Count saturation at the current observation normalization ceiling must be explicit in any future projection contract.

### Anvil option production and pending-choice lifecycle

**Available ItemEngine capability**

- `ItemEngine::grant_component_anvil()` and `grant_completed_item_anvil()` can enqueue a typed `ItemAnvil` containing a kind and a vector of catalog-ID strings.
- `grant_anvil()` validates one to nine unique known options. It rejects empty, duplicate or unknown choices.
- `pending_anvil()` exposes only the front queued anvil. `choose_anvil_option(index)` grants exactly the selected component/item and consumes the queue entry only after a successful grant. Invalid indices leave the pending anvil intact.
- The choice is positional: the implementation has no stable `option_id`, anvil ID, revision, source sequence, producer event ID or explicit completeness metadata.

**Actual audited gameplay reward path**

- `TFTEngine::Impl::grant_round_pve_item_rewards()` currently grants component drops directly with `add_component()` and completed items directly with `add_completed_item()`.
- In the audited `TftEngine.cpp` production path, no call to either `grant_component_anvil()` or `grant_completed_item_anvil()` was found. The anvil grant methods are exercised by `cpp/tests/test_item_engine.cpp`, but the inspected round reward path does not create pending anvils.
- The action/mask/observation code contains a pending-anvil branch, but that consumer capability is not evidence that the normal game path produces pending anvils. Until a production caller is identified, pending-anvil availability is **not produced in the audited runtime path**.
- If an anvil is injected through a future authoritative producer, masks reuse the existing item-choice action head: action type 7 is enabled, option positions occupy the item-inventory mask, and target index zero is a masked sentinel. The PPO anvil block emits pending/kind flags and up to nine option feature rows.
- For each option, the current observation computes one `best_fit` maximum across all current unit profiles (and, for components, across catalog items that can use the component). It is not a per-target fit relation. The schema's `target_fits[]` records with `target_instance_id` therefore have no matching producer in this path.

**Disposition:** the anvil data structure and choice consumer exist, but a live authoritative producer is **not established**. Option IDs, option-set completeness, pending-decision sequence, per-target fit records and source provenance are **not produced**. Keep these fields unavailable; do not infer an anvil from direct PvE item/component grants.

### Architecture reconstruction review

1. **Prior problem:** the semantic entity contract described item instances and anvil option identities as future records without distinguishing current catalog-string storage, aggregate component counts, and the dormant anvil consumer path.
2. **Technical rationale:** treating catalog IDs or vector positions as physical copy identity would make item transfer, duplicate copies, replay and ownership joins ambiguous; treating a consumer branch as a live producer would fabricate decision opportunities.
3. **New responsibility:** this audit slice owns source-backed classification of item catalog metadata, item/component ownership containers, anvil producer availability and actual PPO delivery.
4. **Contracts/invariants:** catalog identity != physical item identity; repeated IDs express multiplicity only; components/inventory/equipment are distinct ownership states; anvil option index != stable option ID; diagnostic snapshot != PPO tensor; heuristic fit != observed fact.
5. **Cross-component impact:** ItemEngine, ItemCatalog, UnitInstance equipment mirror, PvE loot distribution, TftEngine rewards/actions/masks/observations, AuditSnapshot, pybind, Python wrapper, PPO projection, replay and checkpoint lineage.
6. **Objective validation:** source trace of grant/craft/equip/sale/merge/reset; direct PvE reward producer trace; ItemEngine unit tests for queue/choice/transfer; audit-snapshot and pybind field trace; explicit confirmation that no typed item-instance or anvil-option envelope reaches PPO.



## Trait and positioning producer audit — source-backed slice

**Audit status:** partial source audit for #346. The findings below distinguish native/catalog facts, derived strategic assessments, PPO projection, and read-only positioning proposals. No runtime behavior or tensor layout is changed.

### Trait identity, membership and counting semantics

#### Catalog producers

- `ChampionDefinition::traits` is loaded from the active champion catalog and represents static champion-to-trait membership.
- `TraitMilestones.hpp::load_trait_milestones()` loads threshold values from `traits.json` (preferentially beside the selected unit catalog, with the configured repository fallback). It indexes API identifiers and canonical English names; conflicting milestone definitions are rejected.
- `observation_trait_names` is assembled by iterating champion catalog entries and appending each previously unseen trait. This is an ordering derived from catalog iteration, not a separately versioned trait-catalog fingerprint in the observation payload.
- The milestone loader and champion trait membership are distinct inputs. The inspected path does not bind either to a typed per-observation catalog fingerprint or source-sequence envelope.

#### Distinct native counting paths

The current Engine has several non-equivalent trait calculations:

1. **PPO observation counts (`build_observations`, lines around 1305–1368):** counts each catalog trait for each occupied board and bench UnitInstance. It reads `ChampionDefinition::traits`; the inspected `count_traits` path does not add `item.grants_trait`. It therefore represents board + bench catalog membership, not active board synergies and not the complete item-adjusted trait state.
2. **PPO fixed trait block:** emits one value per `observation_trait_names` entry using the board + bench count divided by five and clamped to 1.0. The preceding five-value SYNERGY block instead selects the first five traits in the insertion order of the current accumulated counts. Neither is a lossless typed trait entity collection; counts above five saturate.
3. **Strategic active traits (`update_strategy`):** builds `board_trait_counts` from board units only. For each physical UnitInstance it unions catalog traits with non-empty `item.grants_trait` in a set, so one unit contributes at most once to a given trait. It then emits `StrategyInfo::active_traits` in the current owned-unit `trait_order`. This is the closest current representation of deployed, item-adjusted active-trait counts.
4. **Owned trait counts and `core_traits`:** a separate board + bench aggregation includes item-granted traits, counts each physical owned unit once per trait, orders by count with stable first-seen tie behavior, and selects up to three traits with count >= 2. This is a derived strategic preference, not the active board trait state.
5. **Synergy reward helper:** `count_unique_champion_traits` deduplicates by `champion_internal_id`, not UnitInstance UUID. Multiple physical copies of the same champion therefore contribute only once in this helper. This is not equivalent to active trait counting by physical unit copy.
6. **Composition trait scoring/focus:** weighted scores use unit cost, star level, offensive factors, board milestone levels and focus weights. These are derived strategic assessments, not observed trait counts.

These semantics must remain separate. In particular, catalog membership != item-granted membership; board + bench != deployed board; raw count != activated milestone level; active trait != core trait != composition direction != focus weight; physical-copy count != unique-champion reward count.

#### Delivery boundary

- The native PPO observation contains fixed numeric trait blocks only. It carries neither trait entity records nor field-level provenance, trait source sequence, explicit milestone records, or the catalog fingerprint/order as a typed envelope.
- The audit snapshot path inspected for #346 exposes unit/item state and board diagnostics, but does not establish a dedicated structured trait collection with typed identity, producer sequence and completeness.
- `StrategyInfo::active_traits`, `core_traits`, `composition_direction` and focus diagnostics are not interchangeable with PPO trait features. Existing strategic Shadow snapshots and diagnostics must preserve their own provenance and sequence; their existence does not prove PPO delivery.

**Trait status:** catalog membership and milestone definitions are native/catalog-backed; several aggregates are derived in distinct scopes; structured, sequence-bound trait entities and catalog-version binding are not produced in the inspected PPO delivery path.

### Position identity, spatial mapping and proposal lifecycle

#### Native board geometry

- The board is a fixed 28-slot array. `PositioningEngine` declares a 4-row × 7-column mapping using `row = slot / 7` and `column = slot % 7`.
- The inspected positioning helpers calculate rectangular row/column neighbors (4- or 8-direction) and role preferences. `StrategicPositionPlanner` also uses the same 4×7 decomposition for row/column scoring.
- This proves an internal rectangular slot convention, not canonical TFT hex coordinates, hex adjacency, board orientation, opponent-facing direction, or a versioned mapping to the live game's spatial model. Do not label these indices as canonical hex coordinates.

#### Shadow positioning snapshot and proposal

- `TftEngine.cpp` constructs `StrategicPositionSnapshot` from a correlated native action state: match/player/round/sequence, active composition identity/version, alive state, current board/bench champion-ID arrays, and the exact native masks.
- Its role list is populated from `active->candidate.units` (the active composition candidate), not from a proven `lineup.selected_board / entries / exits / deferred_target_ids` integration chain. The audited builder does not establish that those lineup fields are the producer of the positioning proposal.
- The planner maps candidate roles by `champion_id`, then searches current board and bench slots. Because physical UUID is absent from this snapshot, duplicate copies of one champion are marked ambiguous and skipped rather than guessed.
- A proposal contains champion ID, role, source zone/slot, exact target board slot, current/target score, improvement, reason and status, together with match/player/round/sequence and composition identity/version.
- The planner considers empty board destinations only; it does not implicitly swap occupied units. It checks the relevant native action type, source mask and source→target mask before returning a proposal. This is a read-only recommendation, not execution or legality authority.
- The caller adds the proposed champion/target pair to `requested_move_targets` for subsequent resolution. The separate executor resolution contract and its accepted/unavailable result remain authoritative; a positioning proposal alone does not prove execution.

#### Delivery and unresolved spatial semantics

- The positioning proposal is a Shadow diagnostic/proposal path, not a PPO structured observation. The PPO tensor currently receives aggregate positioning score, frontline/backline ratios and role diversity, not per-unit spatial entities or target proposals.
- The exact source/target slot pair is available in the proposal DTO, but its unit reference is champion-level and becomes ambiguous with duplicate owned copies. No UUID-backed physical source identity is carried.
- The 4×7 row/column mapping and role score are heuristic. Hex adjacency, orientation, enemy-facing side, actual frontline/backline semantics, and a catalog/versioned geometry contract remain unverified.
- No integrated evidence in this slice proves that a selected lineup target, its entries/exits/deferred targets, the current board, the proposal and the executor resolution are one continuous correlated record. The existing proposal carries sequence/composition metadata, but the full lineup→position→executor chain remains a replay acceptance requirement.

**Position status:** native slot indices and read-only role-aware proposal parameters are produced; canonical hex geometry, physical-copy source identity, lineup-chain integration and PPO structured delivery are not established.

### Architecture reconstruction review
